# Conformance harness

Every normative claim maps to an executable proof: a host suite in
`tests/harness/` (which `include!`s the same `modules/common/*_core.rs` sources
the `.fmod` modules ship — see
[model.md](architecture/model.md#one-implementation-one-oracle)), a live graph
driver in `tools/e2e/` that boots the built `.fmod` artefacts under
`fluxor-linux` and asserts real output, or a structural gate in `tools/ci/`.
`fluxor ci` runs all three layers.

## Placement

Retries and compensation belong to the graph, deliberately. A device stage is
pure compute: re-running one that failed yields the same failure, and there is
no effect to undo, because on device an effect is a separate connector `.fmod`
wired into the graph. Retry and rollback therefore belong to the graph and to
the connector that owns the external interaction. Implementing them in the
device executor would give a deployment the appearance of durability with none
of the mechanism.

## Running

```
make test           # the host harness suites
tools/e2e/<x>.sh    # one graph E2E on its own
make ci             # fluxor ci — hygiene + strict module build + harness tests + the E2E and CI gates
```
